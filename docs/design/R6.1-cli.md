# R6.1 — `indexarc` CLI and environment injection

Status: implemented (`bin/indexarc.mjs`, `server/cli.ts`, `server/routes/cli.ts`,
Settings → CLI access). Tests: `server/cli.test.ts`.

## What it does

```
indexarc login                                  # paste a token made in Settings → CLI access
indexarc get STRIPE_SECRET                      # value to stdout (no newline when piped)
indexarc env --label my-app > .env.local        # KEY=value lines
indexarc run --label my-app -- npm start        # child process gets the secrets as env vars
indexarc run OPENAI_API_KEY STRIPE_SECRET -- python app.py
indexarc env --app "Shop backend" --env Production > .env   # one application's keys
indexarc run --app "Shop backend" --env Staging -- npm start
```

`--app` (and `--env`) narrow any selection to one application from the
Applications page; alone, `--app` takes every key of that application and
environment.

Names resolve in three tiers: exact name, case-insensitive name, then as an env
key (`"OpenAI API key"` ↔ `OPENAI_API_KEY`). If a tier matches more than one
secret the request is refused (409) with the candidate ids, and `--id` picks one.
Values are never guessed.

Exit codes: 0 ok · 1 error · 2 usage · 3 vault locked · 4 token missing/rejected.

## Design

**The app stays the only process with the vault key.** The CLI is a thin HTTP
client of the running app. It holds no key and no ciphertext, and it reads
nothing while the vault is locked (423, exit 3). There is no "CLI unlock".

**Scoped token, separate from the pairing token.** The pairing token in
`x-indexarc-token` is the renderer's full-API credential. CLI tokens
(`iax_` + 256 random bits) go in `Authorization: Bearer` and the auth
middleware accepts them on exactly two paths: `GET /api/cli/secret` and
`POST /api/cli/env`. A CLI token on any other path gets 401, even a CLI
management path. So a leaked CLI token can read secrets while the vault is
unlocked, but it cannot change, export, lock or unlock the vault, change
settings, or mint tokens.

**Keyed digests at rest.** `data/cli-tokens.json` stores
`HMAC-SHA256(HKDF(vaultKey, "indexarc:cli-token:v1"), token)`, never the token.
A process that can write the data folder (but has no vault key) cannot add a
working token, and `server/cli.test.ts` covers this. Consequences:
- verification needs the vault key, so locked means 423, which is what we want anyway;
- a re-key (password change, recovery, KDF upgrade) or a password removal
  deletes the file. **Changing the master password revokes all CLI tokens.**
  The UI says so.
- With no master password, the digest falls back to plain SHA-256. In that mode
  every vault file is plaintext anyway.

**Creation re-confirms the master password**, the same way export does. It is
throttled and audited (`cli.token.create` / `cli.token.revoke`). Every read is
audited (`cli.read`, `cli.env`) with the token's name and the secret *name*,
never the value.

**Auto-lock is not extended by CLI reads.** A polling script must not keep the
vault open, so CLI requests do not count as user activity.

**Port discovery.** On listen, the server writes `runtime.json`
(`{url, pid, started_at}`, no secret) to a per-user, machine-local state folder:
`%LOCALAPPDATA%\IndexArc\cli` on Windows, `~/Library/Application Support/IndexArc/cli`
on macOS, `$XDG_STATE_HOME/indexarc` on Linux. It is never `~/.IndexArc`, which can
be the install folder. Override with `INDEXARC_RUNTIME_FILE`.
It removes the file on exit, and it does not overwrite a file owned by another
live process, so a dev server never hijacks the installed app's entry. The CLI
also accepts `--url` / `INDEXARC_URL`.

**Token on the client.** Read from `INDEXARC_TOKEN`, or from the file `login`
writes (`cli-token` in the same folder, mode 0600; override with `INDEXARC_TOKEN_FILE`).

## Packaging

The packaged app disables Electron's `runAsNode` fuse, so the app binary cannot
run the script. Instead the CLI ships as its own executable,
`resources/cli/indexarc(.exe)`: `scripts/build-cli-sea.mjs` (`npm run build:cli`)
bundles `bin/indexarc.mjs` and injects it into a copy of Node as a Single
Executable Application, so users need no Node install. `bin/indexarc.mjs` is
shipped next to it for anyone who prefers their own Node (18 or later).

- **Windows installer:** adds `<install dir>\resources\cli` to the current
  user's PATH (`HKCU\Environment`, no admin rights) and removes it on
  uninstall. A PATH that does not fit NSIS's 8192-character strings is left
  untouched, never truncated. The portable build does not touch PATH; run the
  CLI by its full path.
- **macOS / Linux:** the binary is in the app's `resources/cli/`; link it into
  your PATH yourself (for example `ln -s …/resources/cli/indexarc ~/.local/bin/`).
  The binary is built for the build machine's architecture, so the x64 macOS
  build from an arm64 runner carries an arm64 CLI; use `indexarc.mjs` there.
- **Signing:** the Azure route signs `indexarc.exe` with the app (electron-builder
  signs every `.exe` it copies); the SignPath `app` configuration lists it too.
- **Size:** about 89 MB unpacked (it is a Node binary), about +30 MB on the
  installer.
- **Tests:** `INDEXARC_CLI_BIN=build/cli/indexarc.exe npx vitest run server/cli.test.ts`
  runs the CLI end-to-end tests against the binary; the CI installer test checks
  the PATH entry after install, reinstall and uninstall.

From a checkout: `npm link`, or `node bin/indexarc.mjs`.

## Not in scope

- Writing secrets from the CLI (deliberately read-only for now).
- Reaching the app from another machine: the API stays loopback-only.
- Per-token secret scoping (a token for one label only). The digest file has
  room for a `scope` field; add one when there is demand.
